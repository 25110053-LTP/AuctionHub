Task A: Why Insertion Sort is Suitable for Nearly Sorted Data
Insertion Sort is particularly effective for nearly sorted data because its time complexity is O(n + I), where n is the number of elements and I is the number of inversions (pairs of elements that are out of order). In the context of a bid stream where each new bid is typically about 0.1% higher than the previous one, the incoming data is almost strictly increasing, with only a few elements locally misplaced. Consequently, the number of inversions I is very small (I ≈ O(n)), allowing Insertion Sort to achieve nearly linear O(n) performance. Unlike Quick Sort, which always incurs O(n log n) overhead regardless of the initial state of the array, Insertion Sort directly leverages existing order to minimize element shifts (reaching O(n) in the best case and only degrading to O(n^2) when the data is completely reversed). Beyond speed, the algorithm is stable, operates in-place with O(1) auxiliary memory, and supports online stream processing exceptionally well by inserting each newly arriving bid directly into its proper position.

Task C: When Interchange Sort is Acceptable
Despite its theoretical O(n^2) time complexity, Interchange Sort remains completely acceptable for small datasets (n <= 50). At this scale, the maximum number of comparisons is only about n^2 / 2 (approximately 1,250 operations), resulting in near-instantaneous execution on modern hardware. The primary advantage of this algorithm lies in its concise, readable codebase, which is less prone to logical bugs and requires zero extra memory. Therefore, for QA tools designed to quickly verify small batches of data, code simplicity and maintainability take precedence over asymptotic speed. However, it should never be used for large-scale datasets; for 100,000 bids, the number of comparisons would surge to roughly 5 billion operations, causing severe performance bottlenecks.

Task E: Mechanism and Role of the Median-of-Three Technique
In Quick Sort, the median-of-three technique addresses the weakness of naive pivot selection by choosing the median value among the first, middle, and last elements of the array. Selecting a fixed pivot at the beginning or end of sorted or nearly sorted data causes each partition step to isolate only a single element, degrading time complexity to O(n^2) and risking a stack overflow due to excessive recursion depth. Using the median of three points eliminates the risk of picking an extreme value (minimum or maximum) in common data scenarios, resulting in more balanced partitions and maintaining an average time complexity of O(n log n). Nevertheless, this technique does not completely eliminate the worst-case scenario, as specially crafted adversarial inputs ("median-of-three killers") can still force unbalanced partitions.
